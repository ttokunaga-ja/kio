# 1. 検索応答 — リストの形

## 1.1 決定

**結果は文書単位 1 行。**チャンク単位ではない。

| フィールド | 中身 |
|---|---|
| 文書名 | **検索している時点の名前** (§2) |
| リンク | `evidence_uri` |
| 該当チャンクの特定 | `evidence_pointer` の `byte_start` / `byte_end` (+ `section_id`) |
| `changed_at` | **内容が最後に変わったコミットの日付** |

**`snippet` は廃止する。**クリックで原文を確認する以上、抜粋は要らない。
文書単位に畳んだとき「複数チャンクが当たったらどの抜粋を見せるか」という問題も
同時に消える。

**ハイライトは付けない。**クリック時に該当チャンクを画面中央に置き、表示はフラット。
色や枠が入らない方が、図の閲覧 UI として適切という判断。
**実装上もサーバ側の追加は不要** — スパンは既に応答に入っているので、
スクロール位置の算出はクライアントで完結する。

## 1.2 集約の単位

**`raw_hash` (内容の同一性) で畳む。**

- **リネーム (内容不変)** → `raw_hash` が同じなので **1 行**。同じ内容を 2 行見せる意味はない
- **編集** → `raw_hash` が変わるので**自然に別行**。特別扱いではなく「内容が違うから別」
- **`changed_at`** で区別する。内容が変わったコミットの日付なので、**リネームでは動かない**

材料は durable `chunk_publications` にある。resolver が選んだ qualifying introduction から
コミット → タイムスタンプを解決する。

## 1.3 同一内容が複数スコープにある場合は畳まない

**決定: 集約キーは `(scope_id, raw_hash)`。2 箇所にあれば 2 行、別文書として返す。**

リネームと異なり**どちらも現存する**。そして決め手は利便性ではなく**権限**である:

**階層が違えばアクセス権が違いうる。**`~/work/specs/` の 1 部と共有フォルダの 1 部は
バイト列が同一でも、到達できる経路が同じとは限らない。1 行に畳むと、
**到達できない経路を到達できるかのように見せる**か、逆に到達できる経路を
隠すことになる。内容が同じであることは、**そこへ行ってよいことを意味しない。**

これは §1.2 の「同じハッシュは同じもの」と矛盾しない。リネームは
**同じものが移動した** (現存する場所は 1 つ) が、複製は**同じものが 2 箇所にある**
(現存する場所が 2 つ) で、後者では場所そのものが利用者の要る情報である。

> **判断の記録:** 当初 `scopes[]` を持つ 1 行に畳むことを推奨した。
> 判断基準を「特定の複製に対して操作する必要があるか」に置いており、
> **利用者の意図しか見ていなかった。権限を見ていなかった。**
> 同一内容が同一権限を含意しないという指摘で覆った。

# 2. 文書名 — どの時点の名前を出すか

## 2.1 決定

**検索している時点の名前を出す。**

| 検索 | 出す名前 |
|---|---|
| 現行ツリー | 現在の名前 |
| `--at C` | **C 時点の名前** |
| `--all-history` | その内容が存在した**最後のコミット時点の名前** |

## 2.2 なぜ hash に名前を入れないか

「ファイル名を `raw_hash` の計算に入れれば、リネームが別 identity になって
曖昧さが消える」という案を検討し、**採らない**と決めた。

`raw_hash` は `sha256(原本ファイルのバイト列)` (03 §612) で、パスを含まない。
名前を混ぜると:

- **再 OCR が走る。**03 §843 は「次回 `kio index` は `(raw_hash, tool_profile_hash)`
  一致で up-to-date と判定する」と定める。リネームで hash が変われば正規化から
  やり直しで、スキャン PDF なら **OCR 再実行 = 実費**。参考: このリポジトリの
  fixture の OCR は 1,112 行で $1.07
- **Evidence Pointer が全部切れる。**pointer は `(commit, raw_hash, chunk_hash, span)`
  で、`chunk_hash` は `raw_hash` を入力に含む。リネームで過去の pointer が宙に浮き、
  `verify` は「移動した」と「書き換わった」を区別できなくなる
- **content-addressed store の前提が崩れる。**03 §9 / §261 の dedup は
  同一バイト列が 1 object であることに立っている

**パスは失われていない** — コミットのツリーが path → raw_hash を持つので、
「コミット C でこれは何という名前だったか」は答えられる。足りなかったのは
**どの時点の視点で名前を出すかという規則**だけだった。

識別に名前を入れるのではなく、**表示に「いつの視点か」を入れる。**

## 2.3 付随作業 — eval の M3-2

`--all-history` で内容不変のリネームが**現在の名前**で返るようになると、
**旧名を期待している golden query が外れる。**実数:

| | |
|---|---|
| M3-2 | 16 問 |
| **うちリネーム系** | **13 問** |
| 編集系 | 3 問 |

対象 anchor: `auth-spec.md` / `evidence-pointer-spec.md` / `falcon-migration.md` /
`interview-notes.md` / `kestrel-security.md` / `rag-pipeline.md` / `vendor-eval.md`。

**クエリ文自体は直す必要がない。**実際の文面は
「認証仕様のトークン TTL が 3600 秒だった資料。**今は名前が変わっているかも**」
のように**内容で覚えている**前提で書かれており、旧ファイル名を含まない。
直すのは `expected[].file` の 13 件。

**注意して扱うこと。**`eval/golden-queries.jsonl` は 2026-07-03 の作成以来
**一度も編集されていない** (`git log --follow` でコミット 1 つ)。
その「事前登録されている」性質が価値の一部なので、変更するなら
**日付と理由を記録し、変更前後の Recall を両方報告すること。**
実装を良く見せるための調整ではなく、意図した設計変更への追随である、と
区別できる形で残す。

# 3. クリック先

## 3.1 決定

- **正規化済み markdown 全体**を表示する
- **初期スクロール位置は該当チャンクが画面中央**
- ハイライトなし、フラット表示

## 3.2 いま無いもの [2026-08-11 訂正]

> **初版は「全文を返す口が存在しない。ここが実装の最初の対象」と書いた。誤り。**
> 全文 view は `objects/normalized/ab/cd/<raw64>.<tool64>.g<gen>.md` に
> **既に実体があり**、`normalized_view_path` / `read_normalized_view_at` も既にある。
> **本文を返す新 API は作らない** — パスを返し、リンク先を表示する。

不足しているのは口ではなく**オフセットの変換**である。

- `kio open <pointer>` → **原本**のパス (これは正しい。変更しない)
- `kio view <pointer>` → **チャンク本文だけ**
  (`crates/kio-cli/src/main.rs` の `let text = chunk.text;`) — **ここを削除**し、
  全文 view のパス + view-local span を返す

**罠:** chunk の `byte_start` / `byte_end` は unit-local であり
([03-data-model.md §2.1](../docs/03-data-model.md) 組み立て規則 5)、
view にはヘッダコメントと unit 間の `"\n\n"` 結合が入る。
**pointer の span をそのまま view のオフセットに使うとずれる。**
変換は `kio view` が行い、クライアントに組み立て規則を再実装させない
([05-runtime.md §1.7.2](../docs/05-runtime.md))。

**過去版 (`--at`) に専用経路は要らない。**view のパスは
`(raw_hash, tool_profile_hash, gen)` だけで決まり commit は入らないので、
`--at` は「どの `raw_hash` か」を指す解決手段にすぎない
([05-runtime.md §4.2](../docs/05-runtime.md))。

## 3.3 検索応答に全文を載せない理由 (決定事項)

`--limit` の上限は 100。チャンク本文でも 24 問 × 100 候補の JSON が 1.3MB だった。
文書全体なら桁が変わる。加えて、応答の 1 行が**検証可能なスパン**を指すことが
`verify` を成立させている。

**応答はスパンのリスト、クリック時に全文を取りに行く**の二段構え。

# 4. 画像 — `tasks/rerank-image-space-design.md (git 56a6831)` の決定を上書きする

## 4.1 2 つのヒットの仕方

| ケース | 実体 | リストの名前 | リンク先 |
|---|---|---|---|
| (a) 画像単体が hit | スコープ直下の `.png` 等、それ自体が 1 ユニット | **画像名** | その画像 |
| (b) 文書中の図が hit | 文書の chunk が引用する画像オブジェクト | **文書名** | **文書** (該当箇所へスクロール) |

(b) は「画像がヒットしたら、引用しているチャンクへ解決してから文書として返す」
という一段が要る。

## 4.2 `--mode` に `image` を足す

`text` と対になる。そう置くと、規則が**政策ではなく能力の制約**として書ける:

| mode | 画像に順位が付くか | 理由 |
|---|---|---|
| `text` | **不可** | ベクトルレーンが無い。画像を評価する手段が存在しない |
| `image` | 画像のみ | |
| `vector` | **可** | 同一マルチモーダル空間にある (07 §5.3) |
| `hybrid` | **可** | 同上 |
| `auto` | hybrid のとき可 / text フォールバック時は不可 | |

## 4.3 これは前の決定を取り消す

`tasks/rerank-image-space-design.md (git 56a6831)` §4 は「画像オブジェクト行は**既定のランキングに
出さない**」と確定させていた。**取り消す。**`auto` は通常 hybrid に解決するので、
上の規則では既定でも画像が入る。

前の判断は **text-only の場合を一般化しすぎていた。**text-only で出さないのは
正しく、それは「既定で出さない」とは別のことだった。

## 4.4 `--mode image` の中身

**2 つの層を分けて決める。混同すると話が噛み合わない。**

**候補の層 — 画像候補だけ。**`--mode` は**どの候補クラスを使うか**の軸であって、
リンク先を選ぶ軸ではない。`text` が FTS で到達できる候補に限るのと同じ規則で、
`image` は画像候補に限る。ここに引用元チャンクを混ぜると
`--mode image` が `hybrid` の劣化版になり、軸の意味が壊れる。

**提示の層 — 行が表すのは §4.1 のとおり。**

| ヒットした画像 | 行が表すもの | クリックで行く先 |
|---|---|---|
| 単体の画像ファイル | **その画像** | 画像 |
| **文書中の図** | **その文書** | **文書全体**。該当の図の位置へスクロール |

**文書中の図がヒットしたとき、裸の画像行を返してはならない。**
引用しているチャンクへ解決し、**文書として**返す。クリック先は §3 と同じ
「正規化 markdown 全体 + 該当箇所へスクロール」で、スクロール先が図になるだけ。

つまり `--mode image` の結果リストには、**画像名と文書名が混在しうる。**
候補が画像に限られていることと、行が文書を表しうることは、両立する。

# 5. reranker と RRF

## 5.1 確認済み — 欠けているレーンは既に 0 として扱われる

`crates/kio-search/src/rrf.rs`:

```rust
candidate.rrf_score =
    candidate.text_rank.map(|r| config.w_text / (config.k + r) as f64).unwrap_or(0.0)
  + candidate.vector_rank.map(|r| config.w_vector / (config.k + r) as f64).unwrap_or(0.0);
```

**テキスト側に出てこない候補は 0 が足されるだけ**で、ベクトル側の寄与は満額残る。
画像に対する扱いとして既に正しい。**変更不要。**

## 5.2 案 — reranker を第 3 のランク源にする

reranker は RRF の中に居ない。**プールを組み立てる段 (RRF) の後に、
順序を置き換える別の段**である。だから「テキストスコアを 0 にする」という
操作がそのままでは存在しない。

ただし**第 3 のランク源として RRF に入れる**なら対称になる:

```
rrf_score = w_text/(k+text_rank) + w_vector/(k+vector_rank) + w_rerank/(k+rerank_rank)
```

画像は reranker の出力に現れない → その項が `unwrap_or(0.0)` →
**テキストレーンに現れない画像とまったく同じ扱い。**
「棄権」という特別規則が要らなくなり、既にある仕組みの帰結になる。

**留保 2 点:**

- **`w_rerank` は未測定。**語レーンで、等重み融合が高精度レーンを引きずり下ろすのを
  実測している (`tasks/word-lane-measurement.md (git 56a6831)`)。reranker は役割が違う
  (プールを広げるのではなく精度を上げる) が、**重みは測って決めること**
- **測定済みの +0.125 は「順序を全置換」した場合の値。**融合版は**未測定**

# 6. 実装順序と、決まっていないことの一覧

1. **`kio view` が view のパス + view-local span を返す** (§3.2) — 他の全部の前提
2. **結果の文書単位集約** (§1.2) — `--limit` の意味が「チャンク N 件」から
   「文書 N 件」に変わる。`--offset` / `--cursor` の境界も文書単位になる。
   `max_per_raw_hash = 3` は意味が変わる (削除ではなく、変わったことを記録)
3. **文書名の時点規則** (§2.1) と eval M3-2 の追随 (§2.3)
4. **`--mode image`** (§4.2) — 中身 (§4.4) を先に決める
5. **reranker の統合** (§5.2) — `w_rerank` の測定を伴う

**未決の一覧:**

**`w_rerank` (§5.2) の 1 件のみ。**実測してから決める。判断基準:

| | fixture-B 24 問の Recall@10 |
|---|---|
| reranker なし | **0.7500** (実測済み) |
| 順序を全置換 | **0.8750** (実測済み) |
| RRF 融合 | 未測定 |

`w_text = w_vector = 1.0` 固定で `w_rerank` を掃き、**全置換の 0.8750 を超えるか**を見る。
超えなければ融合しない — 単純な方 (全置換 + 画像を rerank 対象から外す) が勝つ。
低い重みを含めるのは、語レーンで**等重み融合が高精度レーンを引きずり下ろした**
実測があるため (`tasks/word-lane-measurement.md (git 56a6831)`)。

**24 問では 1 問 = 0.0417。これ未満の差は差ではない。**3 モデルが +0.125 で
並んだのを同点と読んだのと同じ基準を当てる。

reranker 統合の実装と同時にしか測れないので、**実装順序としては最後。**

## 決着済みとして畳んだもの

- **同一内容の複数スコープ** → §1.3。権限が理由で**畳まない**
- **`--mode image` の中身** → §4.4。候補は画像のみ、行は文書を表しうる
- **クラス C の判定信号** → **未決ではなかった。**`local_ocr_markdownize` は
  既に区別している (テスト `text_block_boxes_are_not_treated_as_figures`:
  「図の無い散文ページは画像を 1 つも産まない」)。文字に起こせた領域は散文になり、
  図として残した領域は `![](…)` + 画像オブジェクトになる。
  **画像オブジェクトが存在すること自体が OCR の判断**であり、検索時は
  `result_type` がそれを区別している。新しい信号は要らない。
  残る細目は「図から回収したキャプションを adapter が記録しているか」で、
  これは設計判断ではなく実装時の調査項目
